# FELT v2 reproducibility work plan

Status: implemented and validated on 2026-09-06. See
`docs/REPRODUCIBILITY_VALIDATION.md` for acceptance evidence. This file is
retained as the scope and decision record for the cleanup.

## Objective

Create a release-oriented FELT v2 repository that allows another researcher to
restore the documented RAVDESS inputs, install the locked environment, and run
one canonical sequence of commands without repeating the experiments used to
develop the method.

## Fixed scientific decisions

1. Py-Feat 2.0.3 `Detectorv2` is the final extraction method.
2. The seven products generated by `4_generate_visualizations.py` are the
   canonical visualization outputs.
3. Action Units and blendshapes are smoothed in the official release.
4. Material under `01_data/02_output/062/` is historical Py-Feat 0.6.2 output
   and is not part of the FELT v2 production pipeline.

## Reproducibility target

The canonical v2 corpus has:

- 4,904 RAVDESS MP4 files available as source material;
- 2,452 selected full audiovisual inputs;
- 1,440 speech trials and 1,012 song trials;
- 2,452 raw Detectorv2 CSV files;
- 2,452 smoothed CSV files; and
- seven visualization MP4s per trial, or 17,164 MP4 files in total.

Reproducibility will require identical file inventory, schema, frame coverage,
review decisions, and smoothing configuration. CSV numeric values should be
equivalent within documented tolerances. Video products should have the
expected frame counts, dimensions, and view types. Byte-identical outputs may
not be realistic across operating systems, GPUs, and FFmpeg builds, so all
relevant software and hardware provenance must be recorded.

## Phase 0: protect and baseline the current state

1. Compute SHA-256 checksums for the four archives in
   `01_data/02_output/` and their copies in a protected external location.
2. Confirm the corresponding hashes match, not only their file sizes.
3. Record source and output inventories.
4. Capture all current tracked and untracked code/documentation changes in a
   clearly labelled snapshot branch and commit. Do not add `01_data/`.
5. Tag the snapshot as the pre-cleanup state.
6. Create a separate cleanup worktree and branch from the snapshot.
7. Configure the cleanup worktree to read the restored RAVDESS input while
   writing tests and validation outputs to a separate location.

Suggested worktree arrangement:

```text
E:/github_repos/felt          mixed-state reference
E:/github_repos/felt-repro    reproducibility cleanup worktree
<external backup location>    protected output backup
```

## Phase 1: define the canonical v2 contract

Document and validate the following contract:

- Py-Feat 2.0.3 `Detectorv2`;
- batch size one;
- deterministic selection of the 2,452 full audiovisual RAVDESS videos;
- extraction QC before correction;
- duplicate-frame and multiple-face QC, with zero duplicate-frame files in the
  final Detectorv2 extraction;
- targeted missing-output correction;
- approved Challis master cutoffs;
- smoothing of geometry, Action Units, and blendshapes;
- seven canonical videos per trial;
- final QC, archive manifests, and checksums.

## Phase 2: classify and separate repository material

Assign every script and document one status:

- `production`: required to produce the official v2 release;
- `supporting`: QC, review, plotting, packaging, or diagnostics used by the
  production pipeline;
- `experiment`: profiling, smoke investigations, and alternative methods;
- `legacy`: Py-Feat 0.6.2 code or output; or
- `documentation`: active instructions or historical reasoning.

Preserve experiments and legacy material, but place or label them so users do
not mistake them for production steps. Exclude `062/` from every v2 discovery
function and release archive.

## Phase 3: establish one canonical numbered pipeline

The intended user workflow is:

```text
1. verify RAVDESS inputs
2. extract raw Detectorv2 motion
3. audit and correct raw motion
4. apply approved smoothing
5. validate smoothed motion
6. generate the seven canonical videos
7. validate and package the release
```

The normal release-reproduction path must use the committed, approved
`02_code/config/master_cutoffs_v2.json`. Challis cutoff re-estimation remains available as a
scientific verification/calibration workflow, but should not force ordinary
users to make new smoothing decisions.

The existing three older video generators must not compete with the canonical
seven-view renderer. Preserve them as historical or legacy implementations and
promote the seven-view batch renderer to the documented production video
stage.

## Phase 4: make corrections explicit and reproducible

1. Keep duplicate-frame detection in the v2 QC gate and require zero
   duplicate-frame files. The 24-file reviewed multi-face correction belongs
   to the historical Py-Feat 0.6.2 dataset under `062/` and must not be applied
   to Detectorv2 output.
2. Store the known Detectorv2 missing-output correction, including file, frame, and
   forward-fill method, in a versioned correction manifest.
3. Make the correction stage audit the unmodified extraction first.
4. Require observed exceptions to match the approved manifests.
5. Apply corrections while retaining immutable pre-correction evidence.
6. Audit the corrected output and stop on unexpected exceptions.

## Phase 5: remove machine-specific assumptions

Production commands must accept configuration for:

- source and output roots;
- CPU or CUDA device;
- worker counts and Py-Feat DataLoader workers;
- FFmpeg location;
- overwrite, resume, and dry-run modes;
- approved cutoff and correction manifests; and
- log and QC destinations.

Users should never have to edit source constants to run the pipeline. Source
references written into released CSVs should be portable relative identifiers,
not machine-specific absolute paths.

## Phase 6: validation

### Unit tests

Cover filename parsing, input selection, path handling, cutoff loading,
correction manifests, filtering, clipping, visualization paths, and archive
manifests.

### End-to-end smoke test

Run at least one speech and one song trial through every canonical stage,
including all seven visualization views.

### Full-corpus acceptance test

Confirm:

- 2,452 selected source videos;
- 2,452 raw CSVs and 299,854 unique frame rows;
- no frame gaps or duplicate rows after approved corrections;
- 2,452 smoothed CSVs with no smoothing failures;
- 17,164 canonical MP4s;
- expected frame count for every video; and
- complete archive inventories and SHA-256 checksums.

Run full validation in a new output location so existing production artifacts
remain untouched.

## Phase 7: documentation and release

The final documentation should include:

- `README.md`: installation and short quick start;
- `PIPELINE.md`: exact numbered commands;
- `DATASET_PROCESSING_WRITEUP.md`: scientific methods and QC narrative;
- `DATA_DICTIONARY.md`: output columns and ranges;
- `REPRODUCIBILITY.md`: versions, tolerances, provenance, and expected counts;
- `HISTORY.md`: Py-Feat 0.6.2, Py-Feat 2.0.3, and experimental history; and
- `TROUBLESHOOTING.md`: CUDA, TorchCodec, FFmpeg, runtime, and resume guidance.

The final release must contain or identify:

- the code revision and locked environment;
- approved smoothing and correction manifests;
- source-input, extraction, smoothing, visualization, and archive manifests;
- archive SHA-256 checksums; and
- known limitations.

## Completion criterion

The work is complete when a clean checkout can follow the documented commands
against restored RAVDESS input, generate the expected v2 artifact tree, and
pass the complete acceptance checks without consulting experimental notes or
editing production source code.
